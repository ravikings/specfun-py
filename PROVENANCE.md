# Provenance

Every `.f` file in `services/specfun/native/` was fetched from netlib
`specfun` on 2026-09-22:

| File | URL |
|---|---|
| gamma.f, algama.f, psi.f, daw.f, ei.f, erf.f, i0.f, i1.f, k0.f, k1.f, ren.f | https://www.netlib.org/specfun/<stem> |

Upstream listing: https://www.netlib.org/specfun/ (Zhang & Jin,
*Computation of Special Functions*, Wiley 1996; ACM TOMS Algorithm 759).

SHA-256 of every file as packaged was recorded by `nativegate golden
record` in `services/specfun/golden.json` at bind time; any edit that
changes a source file changes the pinned hash, and a rebuild that
changes an answer fails the golden check.

Since nativegate 0.1.3 these are the netlib downloads byte for byte:
upstream marks the machine dialect by commenting every line in both
histories

```fortran
CS    REAL FUNCTION GAMMA(X)
CD    DOUBLE PRECISION FUNCTION DGAMMA(X)
```

and this project selects the DOUBLE PRECISION half with
`nativegate.yaml`'s `dialect: cd`. The resolved code lives in
`native/_expanded/` (regenerated by `ngate generate`); the bytes under
`native/*.f` are exactly what netlib serves and what
`services/specfun/golden.json` pins.

## What was regenerated, not hand-written

Fortran: nothing beyond one documented fetch. Everything else in this
tree — bindings, CMakeLists.txt, the Python package, the pytest
suite, golden.json — is generated by nativegate (>= 0.1.3), and:

```bash
python -m ngate generate specfun
```
from the repository root rebuilds the bindings and the `_expanded`
copies from the committed Fortran.
